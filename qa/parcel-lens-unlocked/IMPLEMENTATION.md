# Parcel magnifier availability after asset unlock

The magnifier previously depended on `parcelState.parcel.geometry`, an asynchronous GIS result rather than an access decision. A pending, failed or empty point lookup removed the control from both locked and unlocked cards. There was no direct paid-status exclusion in PropertyPinPopup; paid status must remain independent of GIS capability.

`propertyParcelContext` now defines eligibility using the existing server-resolved feature gate, a valid real point and the canonical address-privacy rule. Match/payment state and lookup results are not inputs. The popup uses this explicit eligibility rather than geometry availability; the component additionally enforces address privacy, including previously loaded geometry. Initial parcel tabs remain absent until successful activation.

An explicit magnifier click joins any pending point lookup, reuses positive cached evidence, activates only a real uniquely resolved parcel and invokes the existing device-specific camera. Negative/ambiguous lookups are not cached as an exclusion; another click can retry. Source failures are translated and shown inside the stable scrolling popup without removing the magnifier. Switching PINs or disabling eligibility cancels stale activation and its camera callback.

Regression tests cover locked/unlocked properties, unresolved GIS, pending lookup sharing, retry after source failure/missing parcels, cancelled selections, disabled feature gates and both canonical privacy-field spellings. The browser harness can use a canonical asset entitlement (`--unlocked`) and validates it through the actual unlock resolver; screenshots and results are written separately from prior device QA. Browser GIS/auth are explicit synthetic fixtures, not an authenticated production account or live GIS acceptance.

Scope: frontend only. No migration, backend deployment, pricing/payment change, feature-flag/cohort expansion, source/license change, report change or Maxxis evidence consumption.
