# Portfolio card labels and duplicate facts

Confirmed cause: PortfolioDetail used `matches.zip` and `matches.lot`, but these keys were absent from all three dictionaries. It also constructed summary badges and detail rows separately, rendering cap rate and rehab twice. Undefined translated labels were used as React row keys.

The shared PortfolioPropertyFacts presentation now owns one definition per semantic fact ID and one display location. Price, cap rate and rehab remain in summary badges only. Detail rows show type, strategy, rooms, living area, ZIP and lot area. ZIP/lot labels and an explicit living-area label exist in PT/EN/ES, with dictionary fallback. Area values include units; bare native US area fields use sqft, explicitly recorded acres or metric units are retained without conversion. Missing values show an em dash, explicit zero is preserved, ZIP remains text to retain leading zeros. Land omits building-only fields and marks rehab not applicable. Responsive detail rows wrap safely and use one column on phones.

No property mutation, new evidence acquisition, financial calculation change, backend deployment, database migration or feature-flag change. Export generation remains in the existing implementation. The release snapshot contains only this portfolio component/model/styles and dictionary additions, excluding unrelated unfinished enrichment work.

Local validation: 44 targeted tests passed, including contact/email export isolation and report schema/release evidence contracts. Six real PortfolioDetail browser cases passed (desktop/phone, PT/EN/ES, light/dark): no blank fact labels, duplicate fact IDs, repeated rehab value, page errors or horizontal overflow. Desktop and phone Portuguese screenshots were visually inspected. The first test attempt caught a Windows case-insensitive basename collision between the new component and model; the model was renamed before the successful rerun. initial-tests.json preserves that failed attempt.
